Что делает бот

Полный цикл — от webhook PR до комментария в GitHub

Один HTTP-сервис, который подписан на pull_request события репозитория. Кода в репо не клонирует, всё работает по diff'у через GitHub REST API.

1 · Принимает

GitHub шлёт webhook на POST /webhook/github.
Бот проверяет HMAC и отвечает 202 за ≤200 мс.

2 · Анализирует

Скачивает diff, фильтрует мусор, прогоняет pre-scan секретов и отдаёт «чистый» diff в LLM polza.ai.

3 · Пишет в PR

Публикует inline-комментарии на конкретные строки + summary с топ-5 находок. С дедупом по HTML-маркерам.

SQLi

f-string / format / +-конкатенация в execute(), динамические ORDER BY, raw queries.

Hardcoded Secret

AWS AKIA…, GitHub ghp_…, Slack xoxb-…, PEM-ключи, JWT, высокоэнтропийные строки.

XSS

innerHTML, React dangerouslySetInnerHTML, Vue v-html, Jinja |safe, Django mark_safe.

Архитектура · Pipeline

7 этапов обработки одного PR

1
WebhookService — HMAC + dedup + whitelist action opened / synchronize / reopened / ready_for_review
2
GitHubAdapter.fetch_pr_diff — 2 запроса к GitHub API GET /pulls/{n} + GET /pulls/{n}/files (пагинация, ретраи, rate-limit)
3
DiffFilter — выкидывает мусор .md / lock-файлы / бинарники / удалённые файлы / vendor/**
4
FP.pre_llm_scan — регулярки на 9 классов секретов AKIA / ghp_ / sk- / xoxb- / AIza / eyJ / PEM + энтропия на присвоениях
5
LLMClient → PolzaProvider — реальный вызов polza.ai gpt-4o-mini, temperature=0, response_format=json_object, ADR-2 budget
6
FP.postprocess — мерж pre-scan + LLM, дедуп, 15 anti-FP confidence-cutoff, контекст test/example, известные sanitizers
7
CommentPublisher — inline на строки + summary Reviews API + Issues API, идемпотентность через HTML-маркеры

Принципы

  • Pydantic-контракты между всеми компонентами — никто не дёргает чужие словари.
  • Никогда не валит сервис. Каждый этап в try/except, при сбое — graceful degradation.
  • Single-replica (ADR-3): state в памяти, multi-replica запрещён.
  • Идемпотентность × 2: по X-GitHub-Delivery + по repo#pr@head_sha.
  • HTML-маркеры публикации переживают рестарт сервиса — повторного спама в PR не будет.

Почему polza.ai

Российский OpenAI-совместимый шлюз. Доступ из РФ, рублёвая оплата, ~0.18 ₽ за PR. Бюджет 80 ₽ покрывает ≥1700 PR. При недоступности — fallback на Anthropic (post-MVP).

Почему «один процесс»

State лежит в TTLCache в памяти (idempotency, dedup, budget counter). Это ADR-3: мы сознательно отказываемся от Redis/БД ради простоты MVP — single-replica → нет race conditions.

Webhook · POST /webhook/github

Что происходит за первые 200 мс

GitHub  ───POST───▶  /webhook/github
                          │
                          ▼
                  WebhookService.handle(raw_body, headers)
                          │
   1. HMAC: sha256(WEBHOOK_SECRET, body)
      compare_digest с X-Hub-Signature-256   → не совпало 401

   2. X-GitHub-Event == "ping"                → 200 Ignored
      X-GitHub-Event != "pull_request"         → 200 Ignored

   3. seen_delivery(X-GitHub-Delivery)?     → 200 AlreadyProcessed

   4. json.loads(raw_body)                    → 400 BadRequest

   5. action ∈ {opened, synchronize,
                reopened, ready_for_review}?  → 200 Ignored

   6. Pydantic GitHubPullRequestEvent          → 400 BadRequest

   7. SKIP_DRAFTS=true и pr.draft?            → 200 Ignored

   8. mark_pr_in_progress(repo#pr@head_sha) → 200 AlreadyProcessed

   9. BackgroundTasks.add_task(pipeline.process_pr)
                          │
                          ▼
                HTTP 202 Accepted (NFR ≤200 мс)

Двойная идемпотентность

1. GitHub ретраит доставку с тем же X-GitHub-Delivery — игнорируем.
2. На новый коммит в тот же PR (synchronize) приходит новый head_sha — это уже новый анализ, не дубль.

HMAC без подсказок

При несовпадении подписи возвращаем 401 с пустым телом — чтобы атакующий не мог понять, длина ключа правильная или нет.

Whitelist action

Не реагируем на closed, labeled, edited и т.д. — иначе бот будет ходить в polza.ai на каждый чих.

Как ловим уязвимости

Двухконтурная система: pre-scan + LLM

Pre-scan — детерминированно, бесплатно

Регулярки по added-строкам. Срабатывает ДО LLM, чтобы дешёвые находки не зависели от бюджета и доступности polza.ai.

  • aws_access_key_id AKIA|ASIA + 16 chars · critical
  • github_pat ghp_/gho_/ghs_… · critical
  • slack_token xoxb-/xoxp-… · high
  • openai_api_key sk-… · high
  • private_key_pem -----BEGIN…----- · critical
  • jwt eyJ… · medium
  • generic_secret — имя вроде *_token + длина ≥24 + Shannon entropy ≥4.0

LLM — контекстно, polza.ai

Жёсткий system-промпт v1.0.0. Просит только SQLi / Secret / XSS, возвращает строго JSON. Всё остальное бот игнорирует.

{
  "summary": "Found 2 SQLi and 1 hardcoded secret.",
  "findings": [
    {
      "file": "app/views.py",
      "line": 12,
      "class": "sql_injection",
      "severity": "high",
      "message": "f-string SQL без параметризации",
      "suggestion": "cursor.execute(sql, (uid,))",
      "confidence": 0.92
    }
  ]
}

Битый JSON → пустой ответ + warning, pipeline не падает. Невалидное finding в массиве → drop этого finding'а, остальные сохраняются.

Pre-scan ловит «дешёвые» утечки. LLM — контекстные уязвимости в коде.06
FalsePositiveFilter · postprocess

Что отбрасывает фильтр — и почему

Контекстные правила

  • tests/ + hardcoded_secret → severity cap → low (фикстуры, не прод).
  • .env.example / config.example.* → drop hardcoded_secret полностью.
  • placeholder-маркеры YOUR_/REPLACE/FAKE/EXAMPLE/CHANGEME → drop.
  • confidence < 0.5 (порог FP_MIN_CONFIDENCE) → drop.
  • SQLi: рядом ORM/?-параметризация/%s → drop (anti-pattern из vuln_taxonomy §3.3).
  • XSS: whitelist sanitizers: DOMPurify.sanitize, html.escape, bleach.clean, _.escape, sanitizeHtml в окне ±2 строки → drop.

Дедупликация

Один и тот же (file, line, class) попадает и в pre-scan, и в LLM → оставляем тот, у которого confidence выше.

Никогда не валит pipeline

Любой except внутри фильтра логируется как fp_filter_failed, но pipeline идёт дальше с «сырыми» LLM-находками + pre-scan.

Бенчмарк (DoD T-013)

На 14 эталонных FP-кейсах из vuln_taxonomy §6: 10/10 = 100% отфильтрованы (требовалось ≥80%).

Главная защита от перерасхода — BudgetCounter

На каждый LLM-вызов: check_and_reserve(estimated_cost) → если резерв + потраченное > 80 ₽ → BudgetExceeded до отправки запроса. После реального ответа — commit(actual_cost), на ошибке — release(). Даже бесконечный цикл не сожжёт баланс целиком.

Как протестить · шаг 1

Локальный запуск за минуту

# 1. Конфиг — заполни 3 переменные в .env
cp .env.example .env

VCS_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxxxxx
WEBHOOK_SECRET=<длинная случайная строка>
POLZA_API_KEY=pza_xxxxxxxxxxxxxxxxxxxx
ENABLE_TEST_UI=true
HOST=127.0.0.1
PORT=8000

# 2. Зависимости
make install        # runtime
make dev            # + pytest, ruff, mypy

# 3. Поднять сервис
make run            # uvicorn на 127.0.0.1:8000

# 4. Проверка
curl http://localhost:8000/health
{"status":"ok","service":"sunsec"}

Что обязательно в .env

  • POLZA_API_KEY — ключ polza.ai (без него LLM-шаг вернёт provider_unavailable, но pre-scan всё равно работает).
  • WEBHOOK_SECRET — для проверки HMAC от GitHub. Если тестишь только UI — можно любой.
  • VCS_TOKEN — PAT для GitHub. Нужен только когда тестим реальный PR (см. слайд 12).

Чего НЕ делаем

  • Не коммитим .env — он в .gitignore.
  • Не включаем ENABLE_TEST_UI=true в проде — это даёт прямой доступ к polza.ai без HMAC.
  • Не запускаем docker compose --scale sunsec=N — state в памяти, multi-replica запрещён (ADR-3).

TL;DR

Запомни три вещи

1. Это HTTP-сервис

Подписан на pull_request. На webhook → HMAC + dedup + 202 за ≤200 мс. Реальная работа — в BackgroundTasks.

2. Два контура поиска

Pre-scan регулярками (бесплатно, ловит секреты) + polza.ai gpt-4o-mini (контекстно, ловит SQLi / XSS). Бюджет 80 ₽ с kill-switch.

3. Никогда не валится

Каждый этап в try/except, при сбое LLM → graceful degradation: публикуем pre-scan находки + объяснение, почему LLM не сработал.

Как протестить — кратко

  • UI: ENABLE_TEST_UI=true + make run + localhost:8000/ui. Вставляешь код → видишь findings.
  • Unit + e2e: make test — 165 unit + 5 e2e + 20 goldens.
  • Live GitHub PR: ngrok + webhook + test_rep/ → реальные inline-комментарии в PR.
